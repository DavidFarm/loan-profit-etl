The problem

An analyst ran the pricing queries by hand, every month.

A bank receives a vehicle file from an agency each month. Estimated profit per car depends on three things:

  • Energy class of the car
  • Credit risk tier of the customer
  • Base rate (STIBOR 3M), which floats and changes monthly

annual profit = price × (STIBOR 3M + energy margin + risk adjustment) / 100

Each monthly file deliberately contains messy rows: padded and lower-case classes, a missing price, a zero price, an unknown tier, an unknown energy class.

Loan Profit ETL4
Design decisions

Built to fail in the right way.

DecisionWhy
Text stagingA bad value in the file can never fail the load. It is cleaned or rejected with a reason.
Rate fallback, loggedNo rate for the month: use the latest earlier one, and say which. No rate at all: hard stop.
Transactional rebuildThe analyst never sees half a table; a failed run leaves last month's result intact.
Mail outside the main try/catchA broken mail server is a warning, not a failed run.
Failures re-thrownSQL Agent history shows the job as failed when it is.
Re-runnable scriptsEvery script and run is idempotent. Tested.

Loan Profit ETL10
Scope and next steps

What I'd build next.

  • Price the collateral. Depreciation is shown per loan but doesn't move the margin; a lender would price on loan-to-value.
  • Alert on failure. Route Agent job failures to an operator, not only to the log.
  • Real SMTP and a service account. The pipeline mails a local sink today.
  • Loan terms. Today it is year-1 interest on the full price; a real schedule needs a term, a down payment and amortisation.
